# 2.3.2 User Task Matrix

La matriz registra tareas del mundo real, antes de proponer una interfaz. No
afirma que Nexa implemente estas tareas ni que las frecuencias estén medidas. La
evidencia de Mariela y Diego sigue `RESEARCH PENDING`; Carlos se apoya en dos
entrevistas Buyer (`n = 2`) y aún requiere contraste de recepción.

## Escala común de trabajo

| Valor | Frecuencia (F) | Importancia (I) |
| --- | --- | --- |
| Alta | Aparece en la mayoría de los casos que se deben observar o en cada ciclo de la tarea. | Si falla, puede detener, confundir o comprometer materialmente la continuidad del trabajo. |
| Media | Aparece en una parte relevante de los casos o ante condiciones específicas. | Afecta calidad, tiempo o coordinación, pero existe una alternativa temporal. |
| Baja | Aparece excepcionalmente o solo ante una excepción. | Es útil resolverla, pero no define el flujo principal por sí sola. |
| Pendiente | No hay evidencia directa suficiente para proponer una valoración responsable. | No hay evidencia directa suficiente para proponer una valoración responsable. |

Los valores son **working hypotheses** para priorizar entrevistas y pruebas. No
son porcentajes, métricas ni conclusiones generalizables. `OBSERVED n=2` indica
que el tema aparece en las dos fichas Buyer, no que su nivel sea válido para el
mercado.

## Lectura de priorización

1. **Mariela Torres:** H1 debe observar continuidad entre identificación,
   preparación, readiness y handoff sin asignar una frecuencia inexistente.
2. **Diego Ramírez:** H2 debe contrastar el Delivery Attempt, la incidencia y
   la evidencia en condiciones reales de ruta y conectividad.
3. **Carlos Mendoza:** H3 debe completar una entrevista Buyer y un caso de
   recepción antes de convertir visibilidad, verificación o discrepancia en
   comportamiento representativo.

La matriz alimenta los recorridos As-Is y no reemplaza una investigación de
campo. Una actualización posterior debe conservar la fuente, el denominador y
la fecha de cada cambio de valoración.
