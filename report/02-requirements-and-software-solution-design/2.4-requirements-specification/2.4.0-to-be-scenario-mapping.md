# 2.4.0 To-Be Scenario Mapping

## Purpose and status

This document describes the target operating scenarios for the Mobile V1
projection. It is a design and requirements artifact, not evidence that a
Mobile client already exists or that the scenarios have been accepted by
users. The current research campaign and Product Acceptance remain open.

The target separates the physical work from the surface used to record it:
Operations Mobile supports warehouse, dispatch and delivery roles; Buyer
Mobile supports the authorized buyer at handoff and receipt. The API and the
owning Bounded Context preserve the authority of the business facts.

## Target scenario details

### A. Safe access and work context

1. The person returns to the application.
2. The client asks the API to confirm the session and authorized business
   context.
3. The person selects a permitted Tenant/Workspace when more than one is
   available.
4. The client renders only capabilities permitted by the resolved role and
   relationship.

If the session is expired, the context is suspended, or confirmation is not
available, the target state is explicit unavailability. Local state may retain
non-sensitive presentation data or a harmless draft; it cannot authorize a
command or expose protected business information.

### B. Physical operations

1. The Warehouse Operator opens the assigned operational work.
2. The operator identifies a Product/SKU using the accepted input mechanism;
   camera or scanning remains a spike until selected and demonstrated.
3. The client presents the server's current availability, lot and expiry
   information where the contract permits it.
4. The operator records the allowed receiving, allocation or picking fact.
5. The API returns the authoritative result and a traceability reference.

The target does not invent a Scanner Bounded Context. FEFO, lot, expiry,
discrepancy and physical allocation are domain concepts owned by the relevant
contexts and must be confirmed by research and the canonical contracts.

### C. Dispatch and delivery

1. The Dispatch Coordinator reviews prepared work and the delivery context.
2. The coordinator records readiness and an explicit Dispatch Handoff.
3. The Driver or Delivery Operator opens the assigned Delivery and may open an
   external navigation provider for the current stop.
4. The driver records an attempt, outcome, remaining quantity and required
   proof.
5. The driver presents a bounded handoff code to the authorized buyer.

External navigation is a handoff, not continuous background tracking. A
failed network request, duplicate command or unknown result must be visible;
the retry must not overwrite an earlier business fact.

### D. Buyer receipt

1. The Customer Buyer verifies the bounded handoff code against the authorized
   Delivery.
2. The buyer confirms the quantities actually received.
3. The system preserves the buyer receipt separately from the driver's
   Delivery outcome.
4. The buyer may report a discrepancy with reason, affected quantity and
   evidence when required.

Verification of a code is not, by itself, receipt, Proof of Delivery, payment
confirmation or Delivery completion.

## Cross-cutting target rules

| Rule | Target decision | Evidence required before acceptance |
| :--- | :--- | :--- |
| Authority | API and owning Bounded Contexts authorize and persist business facts | Contract test, authorization evidence and accepted user scenario |
| Connectivity | Online-first; local cache, harmless drafts, temporary evidence and retry metadata only | Failure/retry tests and a documented conflict policy |
| History | Driver outcome, buyer receipt, Proof of Delivery, discrepancy, payment and traceability remain distinct facts | Domain review and immutable-history test evidence |
| Location | V1 opens authorized external navigation; no live/background location or ETA authority | Privacy review and device test if the capability is selected |
| Identity | Tenant, Workspace, Human Identity, Workforce Membership, Customer Account and Buyer Relationship stay distinct | Manual story and context-map review |
