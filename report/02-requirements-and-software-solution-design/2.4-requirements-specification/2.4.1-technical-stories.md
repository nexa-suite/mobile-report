# 2.4.1 Technical Stories

Estas Technical Stories describen resultados de habilitación para `Nexa
Operations Mobile` y `Nexa Buyer Mobile`. No son historias funcionales, no
crean Bounded Contexts y no sustituyen los contratos compartidos de Blueprint.
Las tecnologías aceptadas para la proyección de este capítulo son Android
Native/Kotlin, Flutter/Dart para Android e iOS, e iOS Native/SwiftUI. La
presentación Liquid Glass sólo aplica como decisión visual cuando corresponda;
no define una arquitectura ni una capacidad de negocio.

## Agrupación técnica

| Epic | Resultado | Technical Stories |
| :--- | :--- | :--- |
| TECH-EPIC-01 — Contratos y autoridad | Conectar las aplicaciones con contratos REST y preservar la autoridad del servidor. | TS-MOB-001 |
| TECH-EPIC-02 — Bases de plataforma | Preparar las tres tecnologías aceptadas sin duplicar reglas de negocio. | TS-MOB-002..004 |
| TECH-EPIC-03 — Continuidad y capacidades del dispositivo | Proteger estado local, reintentos, identificadores y navegación externa. | TS-MOB-005..008 |
| TECH-EPIC-04 — Calidad y distribución | Integrar notificaciones, accesibilidad, observabilidad y distribución. | TS-MOB-009..012 |

Cada historia usa `Developer` como actor y conserva una pregunta de solicitud y
respuesta en sus criterios Gherkin. Los puntos son estimaciones académicas y la
asignación de Sprint es planificación de Chapter II.

## TS-MOB-001 — Integrar contratos REST con autoridad del servidor

| ID | User | Priority | Epic |
| :--- | :--- | :--- | :--- |
| TS-MOB-001 | Developer | Alta | TECH-EPIC-01 — Contratos y autoridad |

| Story points | Planned Sprint | Referencias compartidas |
| ---: | :--- | :--- |
| 5 | S1 | TS-001, TS-002, TS-003 |

**Title:** Integrar contratos REST con autoridad del servidor

**Description:** Como Developer, deseo integrar contratos REST con contexto explícito de Tenant y autorización del servidor, para que ambas aplicaciones consulten y envíen hechos de negocio sin duplicar autoridad.

**Acceptance Criteria**

- **Scenario: Solicitud con contexto** — **Given** una persona tiene una sesión y un contexto de Tenant autorizados, **When** Developer envía una solicitud REST con el contexto requerido, **Then** la respuesta contiene sólo datos y acciones permitidos para esa relación.
- **Scenario: Solicitud sin contexto** — **Given** una solicitud no contiene contexto válido o autorización suficiente, **When** Developer la envía, **Then** el contrato devuelve un error explícito y no expone datos de negocio.
- **Scenario: Resultado de negocio** — **Given** una operación modifica un hecho de negocio, **When** Developer procesa la respuesta del servidor, **Then** la aplicación conserva el resultado autoritativo y no lo sustituye con un valor local.

**Title:** Proteger el estado local selectivo y no autoritativo

**Description:** Como Developer, deseo proteger caché segura, borradores, evidencia temporal y metadatos de reintento, para conservar continuidad sin presentar el estado local como verdad de negocio.

**Acceptance Criteria**

- **Scenario: Dato permitido** — **Given** el dato está clasificado como caché, borrador, evidencia temporal o metadato de reintento, **When** Developer lo guarda localmente, **Then** queda protegido y vinculado al contexto autorizado.
- **Scenario: Dato autoritativo** — **Given** el dato representa inventario, crédito, pago, compromiso, entrega o recepción, **When** Developer intenta confirmarlo sólo con estado local, **Then** la operación no se presenta como confirmada.
- **Scenario: Cierre de sesión** — **Given** la persona cierra sesión o cambia de Tenant, **When** Developer limpia el contexto local, **Then** el siguiente contexto no puede leer datos protegidos del anterior.

**Title:** Resolver reintentos, resultados inciertos e idempotencia

**Description:** Como Developer, deseo gestionar reintentos, conflictos y resultados inciertos con identificadores durables, para que una interrupción no duplique ni sobrescriba un hecho de negocio.

**Acceptance Criteria**

- **Scenario: Reintento de comando** — **Given** un comando pudo completarse pero la respuesta no llegó, **When** Developer lo reenvía con el mismo identificador de idempotencia, **Then** el servidor devuelve un único resultado sin duplicar el hecho.
- **Scenario: Conflicto de versión** — **Given** el recurso cambió después de la lectura del cliente, **When** Developer envía una mutación con versión obsoleta, **Then** la respuesta identifica el conflicto y no aplica última escritura gana.
- **Scenario: Resultado no confirmado** — **Given** la red interrumpe una operación, **When** Developer actualiza el estado local, **Then** lo presenta como no confirmado hasta recibir respuesta del servidor.
