## Scope of this academic backlog

This section contains the **28 Mobile V1 stories** projected for course
`1ACC0238`. The product catalog remains larger: it contains 73 Mobile stories
across V1, V2, V3 and V4/Future. Stories outside the 28-row projection are not
presented as academic V1 requirements here.

The source of truth for the rows and their scenarios is the Blueprint Mobile V1
catalog and its course projection. This report records the fields needed for
the rubric so that the reader does not have to infer them from another
repository. Research validation, Product Acceptance and Mobile client evidence
remain open at this cut.

### MOB-US-001 — Continue authorized work safely after returning to Nexa

| Field | Value |
| :--- | :--- |
| User / Actor | Mobile User |
| Epic | MOBILE-EPIC-01 — Safe Access & Work Context |
| Priority / Points / Sprint | P1 / 2 / S1 |
| Owning Bounded Context | BC-01 — Tenant & Access Governance |
| Title | Continue authorized work safely after returning to Nexa |
| Description | Como usuario móvil, deseo reanudar de forma segura el trabajo autorizado al volver a Nexa, para continuar mi trabajo sin exponer información protegida. |
| Canonical user story | As a Mobile User, I want to continue authorized work safely after returning to Nexa, so that I can resume my work without exposing protected information. |

**Acceptance criteria (Gherkin):**

- **Scenario: Valid return** — Given a valid, non-revoked session, when the person returns to Nexa, then Nexa confirms identity and exposes only permitted work.
- **Scenario: Expired return** — Given an expired, revoked or malformed session, when the person returns, then Nexa requests identity again and exposes no protected information.
- **Scenario: Unavailable confirmation** — Given identity cannot be confirmed, when the person returns without a connection, then Nexa states that work is unavailable and exposes no protected information.
- **Scenario: Safe retry** — Given the person retries the same return, when Nexa processes it, then no business action is duplicated and no secret is revealed.

## Traceability and review gates

- Product stories are reconciled against the Blueprint projection; the old
  49-story report baseline is not used as the current academic V1.
- Every story needs an owner who can explain the scope and acceptance criteria
  before its implementation or report commit is accepted.
- User research may confirm, refine or reject a proposed story; it may not be
  simulated by filling this table.
- A story is not marked implemented, validated or accepted from its title,
  Gherkin text, API existence or report structure alone.
