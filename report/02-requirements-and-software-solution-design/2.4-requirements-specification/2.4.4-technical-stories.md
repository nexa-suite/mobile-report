# 2.4.4 Technical Stories

## Alcance y autoridad

Este registro contiene la proyección académica de Technical Stories que tienen
una obligación técnica no dirigida directamente a una persona usuaria de
Mobile. Actor de todas las historias: **Developer**. Cada historia permanece
PLANNED o OPEN hasta que exista evidencia; ninguna afirma implementación,
Product Acceptance o Production Readiness.

El registro es una proyección mínima del curso, no una copia del catálogo
transversal. Las fuentes compartidas conservan sus Technical Stories y
autoridad:

- blueprint/01-shared/product/requirements/technical-stories.md
- blueprint/01-shared/product/requirements/README.md
- blueprint/90-academic/mobile/course-1acc0238/architecture-projection.md
- blueprint/90-academic/mobile/course-1acc0238/implementation-evidence-plan.md
- blueprint/03-mobile/architecture/technical/local-storage.md
- blueprint/03-mobile/architecture/technical/synchronization.md

La proyección no introduce endpoints, Bounded Contexts, proveedores ni
decisiones de framework. REST, autorización, invariantes y hechos de negocio
siguen siendo responsabilidad del API y del Bounded Context owner.

## Technical Story details

### TS-MOB-001 — Integrate internal REST contracts with server authority

| Field | Value |
| :--- | :--- |
| Actor | Developer |
| Technical outcome | Integrate the observed internal REST contracts required by the Mobile V1 projection. |
| Why | Keep business authorization, lifecycle and durable facts in API/Bounded Context owners. |
| Affected product / surface | Operations Mobile; Buyer Mobile; API |
| Source requirement | Shared TS-001, TS-006 and TS-007; MOB-US-001..049 |
| Acceptance evidence required | OpenAPI snapshot, story-to-contract mapping, authorized/unauthorized responses and test output. |
| Milestone | TB1–TB2 |
| State | PLANNED; no Mobile client evidence asserted |

- **Given** a selected contract is documented in the current OpenAPI source,
  **When** Mobile consumes it, **Then** the client preserves server response,
  authorization and explicit error states.
- **Given** a contract is absent or its business mapping is uncertain,
  **When** the integration is planned, **Then** the report records the gap and
  does not invent an endpoint.
- **Given** a retry returns an unknown result, **When** the client renders it,
  **Then** it does not claim a business success locally.

### TS-MOB-004 — Handle retries, unknown results and idempotency

| Field | Value |
| :--- | :--- |
| Actor | Developer |
| Technical outcome | Make retry and conflict behavior explicit for retry-sensitive Mobile commands. |
| Why | Preserve immutable history and avoid duplicate inventory, Delivery or receipt facts. |
| Affected product / surface | Operations Mobile; Buyer Mobile; API |
| Source requirement | Shared TS-005 and TS-019; synchronization boundary |
| Acceptance evidence required | Timeout, duplicate command, stale state and recovery tests with durable result evidence. |
| Milestone | TB1–TB2 |
| State | PLANNED |

- **Given** a command response is unknown, **When** the user retries, **Then** the
  UI shows unresolved state until the server returns a durable result.
- **Given** the same idempotency identity is received twice, **When** the API
  processes it, **Then** it returns one durable outcome without duplicating a fact.
- **Given** another actor changed the source state first, **When** the stale
  command arrives, **Then** the conflict is explicit and no last-write-wins
  overwrite occurs.

## Evidence boundary

Technical Story completion requires the listed evidence and responsible review.
A source contract, report structure or planned milestone alone is insufficient.
The report keeps technical, UX, i18n, accessibility, Product Acceptance, System
Acceptance and Production Readiness verdicts separate.
