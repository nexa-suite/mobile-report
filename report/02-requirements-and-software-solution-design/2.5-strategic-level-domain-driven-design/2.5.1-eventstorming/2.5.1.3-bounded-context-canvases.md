# 2.5.1.3 Bounded Context Canvases

Los Bounded Context Canvases deberán seguir el límite y la autoridad de los 11 contextos aceptados por Nexa. Para cada canvas se deberá documentar el propósito, el lenguaje del contexto, sus reglas, capacidades, dependencias y decisiones de diseño.

| Código | Bounded Context |
|---|---|
| BC-01 | Tenant & Access Governance |
| BC-02 | Customer & Buyer Relationships |
| BC-03 | Catalog & Commercial Policy |
| BC-04 | Sales Commitment |
| BC-05 | Inventory Availability |
| BC-06 | Fulfillment & Delivery |
| BC-07 | Credit & Receivables |
| BC-08 | Payments |
| BC-09 | Business Documents |
| BC-10 | Notifications |
| BC-11 | Business Traceability |

No se elaborará un canvas independiente para Operations Mobile o Buyer Mobile porque son proyecciones de producto.

## Canonical canvas index

Este índice convierte el catálogo aceptado en una lista de trabajo para los
canvases. Los campos son una síntesis del Blueprint; no sustituyen los seis
pasos de elaboración ni la crítica de diseño requerida por la rúbrica.

| Código | Propósito / clasificación | Invariante o autoridad a discutir | Estado del canvas |
| :--- | :--- | :--- | :--- |
| BC-01 | Tenant, Workspace, identidad, membresía y acceso; Supporting | Tenant es frontera de aislamiento; scope ambiguo falla cerrado | `TARGET / CANVAS_PENDING` |
| BC-02 | Customer Account y Buyer Relationship; Supporting | Relación de proveedor y comprador requiere aprobación y Tenant | `TARGET / CANVAS_PENDING` |
| BC-03 | Product, SKU, oferta y política comercial; Supporting | Product ≠ SKU; precio/términos se revalidan en submit | `TARGET / CANVAS_PENDING` |
| BC-04 | Purchase Request, Commercial Commitment y Sales Order; Core | Compromiso y transferencia a SO son autoritativos y atómicos | `TARGET / CANVAS_PENDING` |
| BC-05 | Stock físico, lotes, disponibilidad y Physical Allocation; Core | Sellable Availability, backing, FEFO y disposición son autoridad de inventario | `TARGET / CANVAS_PENDING` |
| BC-06 | Fulfillment, picking, packing, dispatch y delivery; Core | POD es inmutable; handoff, outcome, receipt y discrepancy permanecen separados | `TARGET / CANVAS_PENDING` |
| BC-07 | Credit Reservation, Available Credit y Receivable; Supporting | Payment ≠ Receivable; correcciones preservan historia | `TARGET / CANVAS_PENDING` |
| BC-08 | Payment y traducción del proveedor; Generic | Callbacks se deduplican; estado es provider-neutral | `TARGET / CANVAS_PENDING` |
| BC-09 | Documentos emitidos, numeración y evidencia; Generic | Emitido es inmutable; reemplazos no mutan la historia | `TARGET / CANVAS_PENDING` |
| BC-10 | Intent, canal, entrega, retry y fallo de notificación; Generic | Fallo de notificación no modifica el hecho de origen | `TARGET / CANVAS_PENDING` |
| BC-11 | Timeline durable de hechos de negocio; Supporting | Append-only, tenant-scoped; no reemplaza Security Audit ni fuente | `TARGET / CANVAS_PENDING` |

Cada canvas debe completar: `Context Overview Definition`, `Business Rules
Distillation & Ubiquitous Language`, `Capability Analysis`, `Capability
Layering` cuando aplique, `Dependencies Capture` y `Design Critique`. El
reviewer debe registrar qué proviene del Blueprint, qué es decisión del equipo
y qué permanece abierto.
