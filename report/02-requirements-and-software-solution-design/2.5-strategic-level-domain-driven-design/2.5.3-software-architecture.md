### 2.5.3. Software Architecture

La arquitectura se expresa con C4. La fuente semántica canónica vive en
`nexa-suite/blueprint` en el commit `89f41421a9aa132d5cf565ed6d22154d1bdca5e0`;
este informe sólo conserva exports generados con la procedencia indicada en el
[manifiesto Wave 3](../../assets/chapter-2/provenance/wave3-construction-blueprint.md).
Nexa mantiene una API modular como autoridad de negocio. Un Bounded Context
delimita lenguaje y responsabilidad; no equivale a un Container C4, paquete,
schema ni unidad de despliegue.

#### Vistas C4

| Vista | Alcance | Lectura |
| :--- | :--- | :--- |
| L1 System Context | Nexa, actores y dependencias externas V1. | Límite del sistema y relaciones externas. |
| L2 Container | Superficies, API y almacenamiento. | Unidades ejecutables o de almacenamiento. |
| L3 Technical Architecture | Responsabilidades técnicas dentro de Nexa API. | Presentación, aplicación, dominio, contexto, persistencia, integraciones y confiabilidad. |
| L3 Domain Ownership Mapping | Los once Bounded Contexts sobre responsabilidades técnicas. | Ownership lógico, no un componente ni Container por contexto. |
| Dynamic | Siete workflows críticos ordenados. | Límite atómico antes de publicación durable asíncrona. |
| Deployment | Nodos lógicos de ejecución y datos. | Topología sin convertir contextos en nodos. |

#### Decisiones de arquitectura

- Nexa API mantiene autoridad de negocio, autorización, transacciones e
  idempotencia.
- PostgreSQL se comparte físicamente; cada contexto conserva ownership lógico
  y alcance explícito de Tenant/Workspace.
- Object Storage se accede mediante ports/adapters y referencias autorizadas.
- Website, Platform, Buyer Portal, Operations Mobile y Buyer Mobile son
  superficies de producto, no Bounded Contexts.
- Operations Mobile usa Android/Kotlin/Jetpack Compose. Buyer Mobile usa
  Flutter/Dart en Android+iOS. Ambas son Containers TARGET V1 aceptados; no
  prueban implementación integrada ni aceptación de producto.
- Los componentes C4 muestran responsabilidades arquitectónicas y tecnología,
  no paquetes ni clases Java.

Las vistas son modelos de arquitectura. No demuestran por sí mismas runtime,
integraciones ejecutadas, autorización efectiva o preparación de producción.

#### Mapeo de ownership y workflows

La lente de mapeo conserva explícitamente los once Bounded Contexts sin
convertirlos en paquetes, módulos Spring Modulith, schemas PostgreSQL ni
Containers C4.

![Mapeo C4 TARGET de ownership de dominio](../../assets/chapter-2/c4/Nexa-API-DomainOwnershipMapping-TARGET.svg)

Las vistas dinámicas cubren Submit Purchase Request, Confirm Direct Order,
Convert Purchase Request to Sales Order, Fulfillment/Pick/Dispatch/Handoff,
Delivery partial/continuation, Buyer handoff/receipt/discrepancy y
Payment/Receivable application. Cada flujo conserva contratos explícitos entre
contextos; una flecha no crea propiedad de objetos ajenos.
