# 2.5.3 Software Architecture

La arquitectura estratégica se expresa con C4 y Structurizr. Nexa es un único
sistema B2B SaaS multi-tenant; la fuente moderna del API observada implementa
un Spring Boot modular monolith. Los Bounded Contexts no se convierten
automáticamente en containers, procesos o deployments.

componentes permanece como sección descriptiva sin numeración artificial.

## Decisiones de arquitectura

- La fuente del API revisada declara Java 25, Spring Boot 4.1.x y Spring Modulith dentro de un único modular monolith.
- El diseño aceptado y la configuración local usan PostgreSQL compartido con ownership lógico por contexto y alcance explícito de Tenant/Workspace; esta revisión no afirma una ejecución runtime concreta.
- Object Storage se delimita detrás de ports/adapters; la configuración local existe, pero el proveedor y su ejecución permanecen fuera de esta evidencia.
- Website, Platform, Buyer Portal, Operations Mobile y Buyer Mobile son superficies o containers; no son Bounded Contexts.
- No se agrega Kafka, otro broker, una segunda base de datos, Kubernetes, microservicios ni transacciones distribuidas sin evidencia adicional.

## AS-IS, TARGET y evidencia

Las vistas distinguen implementación observada, diseño V1 aceptado y evolución
 futura. Operations Mobile y Buyer Mobile aparecen como proyecciones V1 y su
 presencia en C4 no prueba framework, build, runtime, aceptación de producto ni
 preparación de producción. La fuente semántica es el Structurizr DSL canónico;
 las imágenes se leen como exports de diseño, no como evidencia de ejecución.

## Software Architecture Components

Los componentes se muestran como lentes selectivos dentro de Nexa API o de las
superficies clientes. No son Bounded Contexts, no redefinen el Context Map y no
sustituyen el diseño táctico posterior.

### Familias de componentes del API

| Familia C4 | Capacidades observadas en el diseño | Límite estratégico |
| :--- | :--- | :--- |
| Identity, Tenant & Customer | Identity, tenant/workspace, customer y buyer relationship adapters. | Sirve BC-01 y BC-02 sin fusionar sus autoridades. |
| Commercial & Inventory | Catálogo/política, compromiso comercial, disponibilidad y protección. | Proyecta BC-03/04/05; no convierte cada módulo en container. |
| Fulfillment & Delivery | Fulfillment, dispatch, handoff, delivery y continuidad. | Sirve BC-06 y conserva delivery outcome/POD separados. |
| Credit, Payment & Documents | Crédito/receivables, pagos, documentos y provider ACL. | Sirve BC-07/08/09 sin crear un Finance context genérico. |
| Integration Reliability | Outbox, inbox/deduplication, retries y publicación de hechos. | Soporta BC-10/11 sin ser un nuevo Bounded Context. |

Estas familias representan cortes de lectura del API. El ownership lógico sigue
siendo el de los once contextos; PostgreSQL compartido no crea un propietario
común.
