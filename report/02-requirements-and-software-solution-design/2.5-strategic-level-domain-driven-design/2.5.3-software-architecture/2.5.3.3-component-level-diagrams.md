# 2.5.3.3 Software Architecture Component-Level Diagrams

Esta sección cubre el componente de arquitectura solicitado por el enunciado.
Los diagramas deberán mostrar componentes dentro de los containers, sin
confundirlos con Bounded Contexts.

Las vistas Mobile se tratarán como proyecciones V1 TARGET / PLANNED / PROPOSED;
las vistas del API se presentarán según la evidencia de implementación o de
diseño disponible.

## Límites candidatos de componentes

| Container | Componentes por verificar | Regla de límite |
| :--- | :--- | :--- |
| Nexa API | Interface/REST adapters, application handlers, domain modules, persistence ports, integration adapters | Un componente puede servir una capability de un Bounded Context; no se convierte automáticamente en contexto o deployment |
| Operations Mobile | Session/context client, work projection, command/retry coordinator, evidence staging and navigation adapter | Toda mutación de negocio permanece autorizada por el API; los recursos del dispositivo requieren permiso y fallback |
| Buyer Mobile | Session/context client, delivery projection, handoff/receipt flow, discrepancy evidence and notification/deep-link handler | Verification, receipt y discrepancy permanecen como estados y hechos separados |

Son límites de diseño candidatos, no una afirmación de que los componentes
existan en el repositorio Mobile actual. El diagrama final debe nombrar el
container seleccionado, el archivo o decisión aprobada, sus interfaces,
dependencias y revisión de render.

## Estado de evidencia

Existen vistas de diseño de componentes, incluidas
Nexa-Operations-Mobile-TARGET y Nexa-Buyer-Mobile-TARGET. Falta seleccionar
los containers que se detallarán, incorporar los exports y registrar la
explicación y revisión humana de responsabilidades e interacciones.
