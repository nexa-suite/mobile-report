#### 2.5.3.3. Software Architecture Deployment Diagrams

El Deployment Diagram muestra nodos, límites y relaciones de runtime. No
representa Bounded Contexts, módulos internos ni una base de datos por contexto.

##### Purpose and interpretation

La vista explica cómo Nexa API, PostgreSQL, Object Storage y clientes
planificados se relacionan en una topología provider-neutral. La imagen no
acredita deployment ejecutado, build Mobile, secretos, backups, rollback,
observabilidad ni preparación de producción.

##### Elementos de la topología

| Elemento | Papel en el diseño | Condición para confirmar ejecución |
| --- | --- | --- |
| Nexa API | Conserva autorización, transacciones críticas, idempotencia y autoridad de negocio. | Artefacto identificable y entorno verificable. |
| PostgreSQL | Persistencia compartida con ownership lógico por contexto. | Instancia, esquema y controles observables. |
| Object Storage | Almacena bytes de documentos y evidencia mediante referencias autorizadas. | Proveedor, bucket y acceso verificables. |
| Operations Mobile y Buyer Mobile | Clientes del API; no son nodos autoritativos ni backends separados. | Build, dispositivo o emulador y flujo observado. |
| Payment, Email y Maps providers | Dependencias externas abstractas. | Selección de proveedor y prueba reproducible. |

##### Topología y límites

- Nexa API conserva decisiones transaccionales y reglas de negocio.
- PostgreSQL compartido no implica una base de datos por Bounded Context o por
  Tenant.
- Object Storage no implica URL pública para documentos o evidencia.
- Los clientes móviles solicitan comandos al servidor; no sustituyen su
  autorización.
- Las dependencias externas requieren contratos explícitos antes de integrarse.
