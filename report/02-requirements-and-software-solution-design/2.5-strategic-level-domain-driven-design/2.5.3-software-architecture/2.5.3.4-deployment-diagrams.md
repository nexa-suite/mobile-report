# 2.5.3.4 Software Architecture Deployment Diagrams

El diagrama de despliegue debe mostrar nodos y relaciones de runtime, no
Bounded Contexts ni módulos internos. La única vista que puede afirmarse como
AS-IS es la que se compruebe mediante configuración, ejecución y captura del
entorno correspondiente.

## Vistas a documentar

| Vista | Contenido permitido | Estado |
| :--- | :--- | :--- |
| Local AS-IS | Nexa API, PostgreSQL, Object Storage y superficies existentes sólo cuando el compose, configuración y ejecución sean verificables | Preparación documental; ejecución no registrada en este corte |
| V1 TARGET | Operations Mobile y Buyer Mobile como clientes planificados que consumen la API; proveedor de mapas, email y pagos abstractos | `TARGET V1 / PLANNED / PROPOSED`; no se ha demostrado runtime desplegado |
| Cloud/producción | Proveedor, redes, secretos, backups, rollback, disponibilidad y observabilidad | OPEN; requiere evidencia de despliegue y operación |

La fuente canónica de C4 observada es
`blueprint/01-shared/architecture/c4/structurizr/deployment/deployment.dsl`,
con exports AS-IS y V1 TARGET. El informe debe conservar la procedencia y la
etiqueta de cada vista; una imagen exportada no demuestra que el runtime se
haya ejecutado.

## Límites de la topología

- PostgreSQL es infraestructura compartida con ownership lógico por Bounded
  Context; no se representa una base de datos por contexto o por Tenant.
- La API conserva autorización, transacciones críticas, idempotencia y
  autoridad de negocio; el cliente móvil no se convierte en nodo autoritativo.
- Object Storage contiene bytes de documentos o evidencias con autorización
  de objeto; no se asume que una URL pública exista.
- Maps & Geolocation Provider se limita a la apertura autorizada de navegación;
  no implica tracking continuo.
- Email Delivery Service y Payment Provider son integraciones abstractas hasta
  que exista un proveedor elegido y una prueba reproducible.
