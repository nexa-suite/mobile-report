## Diseño relacional objetivo de BC-06

La fuente SQL contiene dieciséis tablas. La siguiente lectura resume PK, FK,
unicidad y checks para que el revisor pueda contrastar la imagen con el SQL.
El SQL es la autoridad del modelo objetivo.

| Tabla | PK | FKs internas | Unicidad / checks relevantes |
| :--- | :--- | :--- | :--- |
| `fulfillment` | `fulfillment_id` | —; `sales_order_id` es referencia estable externa | `status` enum explícito; `version >= 0`; `tenant_id` y `workspace_id` requeridos |
| `fulfillment_line` | `line_id` | `fulfillment_id → fulfillment` | `UNIQUE (fulfillment_id, sku_id)`; planned `> 0`; picked entre `0` y planned |
| `picking_result` | `picking_result_id` | `fulfillment_id → fulfillment` | `status ∈ STARTED, CONFIRMED, DISCREPANCY`; picker y timestamps requeridos |
| `picking_discrepancy` | `discrepancy_id` | `picking_result_id → picking_result`; `fulfillment_line_id → fulfillment_line` | `kind` enum; `quantity > 0` |
| `delivery` | `delivery_id` | `fulfillment_id → fulfillment` | `status` enum; destination snapshot requerido; `version >= 0` |
| `delivery_assignment` | `assignment_id` | `delivery_id → delivery` | operador y `assigned_at` requeridos; desasignación separada |
| `delivery_attempt` | `attempt_id` | `delivery_id → delivery` | `UNIQUE (delivery_id, attempt_number)`; attempt `> 0`; outcome enum |
| `delivery_attempt_line` | `line_id` | `attempt_id → delivery_attempt`; `fulfillment_line_id → fulfillment_line` | `UNIQUE (attempt_id, fulfillment_line_id)`; received entre `0` y attempted |
| `delivery_quantity_outcome` | `outcome_id` | `attempt_id → delivery_attempt` | `UNIQUE (attempt_id, sku_id)`; fulfilled/short no negativos |
| `delivery_handoff_token` | `delivery_handoff_token_id` | `delivery_id → delivery`; `delivery_attempt_id → delivery_attempt` | token hash hexadecimal; `expires_at > issued_at`; status; idempotency por issuer |
| `buyer_receipt_fact` | `buyer_receipt_fact_id` | delivery, attempt y `handoff_token` | `UNIQUE (delivery_id, delivery_attempt_id)`; idempotency por buyer; accepted `<=` driver delivered |
| `proof_of_delivery` | `pod_id` | `delivery_id → delivery` | `UNIQUE (delivery_id)`; status `CAPTURED/SEALED/REJECTED`; evidencia capturada |
| `proof_of_delivery_addendum` | `addendum_id` | `pod_id → proof_of_delivery` | razón y actor requeridos; corrección append-only |
| `temperature_evidence` | `evidence_id` | `delivery_id → delivery` | `UNIQUE (delivery_id, captured_at, source)`; lectura y fuente requeridas |
| `temperature_excursion` | `excursion_id` | `delivery_id → delivery`; `evidence_id → temperature_evidence` opcional | status `OPEN/HOLD/DISPOSITIONED/CLOSED`; razón y apertura requeridas |
| `continuation_delivery` | `continuation_id` | `parent_delivery_id → delivery` | snapshot restante requerido; status de continuación explícito |

Los IDs de `SalesOrder`, `SKU`, `PhysicalAllocation`, customer, buyer y
operator son referencias estables no propietarias en el diseño objetivo. La
tabla no crea FK inter-contexto sólo porque las tablas vivan en PostgreSQL.

## Correspondencia con persistencia API observada

El registro de persistencia documenta una consulta de PostgreSQL local sobre API
`380e2427bc3883f23fbd7e9a82d452888f2074a8`, con migraciones `V91` y `V93` entre
las fuentes revisadas. Esta evidencia es `AS-IS/PARTIAL`, no la aceptación del
modelo académico.

| Diferencia a revisar | API/PostgreSQL observado | Modelo objetivo BC-06 | Interpretación |
| :--- | :--- | :--- | :--- |
| Nombres e identidad | Muchas tablas usan `id`, además de columnas de scope y legacy | Usa nombres explícitos como `delivery_id` y `attempt_id` | No renombrar la evidencia observada sin una migración aprobada |
| Fulfillment | `logistics.fulfillment` y campos adicionales, incluidos `physical_allocation_id` y actor | `fulfillment` y `fulfillment_line` separan líneas/relaciones objetivo | Requiere reconciliación de esquema, no inferencia de equivalencia |
| Dispatch | `logistics.dispatch_order` existe en AS-IS | La vista objetivo separa Fulfillment y Delivery | `DispatchOrder` se registra como evidencia actual, no se agrega silenciosamente al diagrama objetivo |
| Handoff/receipt | `logistics.delivery_handoff_token` y `logistics.buyer_receipt_fact` observados con RLS | Tablas objetivo con hash, expiración, binding e idempotencia | Contrato Mobile aditivo; token no equivale a recepción |
| POD/temperatura | tablas y triggers de ciclo/inmutabilidad observados | POD, addendum, evidencia y excursión explícitos | Persistencia parcial; cierre depende de ownership y revisión humana |
| BC-06 / BC-11 | Algunas filas de evidencia se mantienen como `BC-06 + BC-11` pendiente | Business Traceability es un BC separado | La propiedad lógica debe aprobarla arquitectura/datos |

La evidencia reproducible está en el [API persistence evidence
register](../../../../../delivery-checklists/api-persistence-evidence-register.md)
y el inventario de fuentes/exportaciones en el [architecture and diagram
evidence register](../../../../../delivery-checklists/architecture-render-evidence-register.md).
