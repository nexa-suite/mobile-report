#### 3.1.4.6. Mapa de navegación y flujos por trabajo Mobile

Esta guía agrupa los user flows por objetivo y los wireflows por pantalla de
entrada, ruta y recuperación. Complementa los diagramas detallados de
[wireflows](./3.1.4.2-mobile-application-wireflows.md) y
[user flows](./3.1.4.4-mobile-application-user-flows.md); no sustituye sus
decisiones funcionales ni la evidencia de implementación del
[capítulo 4](../../../04-product-implementation-and-validation/4.2-landing-page-and-mobile-application-implementation/4.2.5-operations-mobile-wave-4-evidence.md).

Las etiquetas Owner, Sales, Warehouse, Logistics, Driver y BOM describen
trabajos y personas del informe. Operations Mobile no asigna esos perfiles: el
servidor confirma la sesión, Tenant, Workspace, Membership y permisos. El hub
presenta únicamente las entradas autorizadas. En particular, el código no
declara un rol de aplicación llamado `Owner`; este mapa relaciona esa persona
con la vista operativa si el servidor concede `dispatch.read`.

Los nombres entre comillas son etiquetas del hub actual; los identificadores
entre paréntesis son claves de ruta de `CONNECTED_OPERATIONS`. `OperationsWorkEntryScreen`
es el hub común, `AccessScreen` gestiona acceso y sesión, y
`ContextChooserScreen` selecciona o cambia el contexto. Una ruta modelada o
implementada no demuestra que su resultado comercial u operativo haya sido
validado. La evidencia efectivamente observada se informa por separado en el
capítulo 4.

##### User flows — objetivo, decisión y recuperación

Cada subgrafo representa el objetivo principal, un resultado esperado y una
salida segura para permisos faltantes, información desactualizada o respuesta
incierta. Los caminos operativos detallados y su trazabilidad a historias están
en los diagramas de [user flows](./3.1.4.4-mobile-application-user-flows.md).

```mermaid
flowchart TB
    Start["Abrir Operations Mobile"] --> Session{"¿Sesión y contexto actuales confirmados por el servidor?"}
    Session -->|No: expirada o revocada| Access["AccessScreen: autenticarse o reanudar sesión"]
    Access --> Start
    Session -->|No se puede confirmar| Safe["No mostrar trabajo protegido; reintentar o volver a acceso"]
    Session -->|Sí| Hub["OperationsWorkEntryScreen: ver entradas autorizadas"]

    subgraph Owner["Owner — revisar prioridad operativa"]
      O1["Abrir Vista operativa"] --> O2["Revisar trabajo preparado y frescura"]
      O2 --> O3{"¿El hecho sigue vigente y pertenece al alcance?"}
      O3 -->|Sí| O4["Abrir el proceso propietario para seguimiento"]
      O3 -->|No / sin permiso| O5["Actualizar o regresar; conservar el estado confirmado"]
    end

    subgraph Sales["Sales — atender una relación autorizada"]
      S1["Buscar Customer y relación Buyer"] --> S2["Consultar catálogo o registrar visita"]
      S2 --> S3["Preparar solicitud o revisar compromiso"]
      S3 --> S4{"¿La respuesta del servidor confirma el cambio?"}
      S4 -->|Sí| S5["Mostrar el estado comercial confirmado"]
      S4 -->|No / incierta| S6["Corregir datos o consultar la solicitud antes de repetir"]
    end

    subgraph Warehouse["Warehouse — identificar y registrar trabajo físico"]
      W1["Identificar SKU por escaneo o búsqueda manual"] --> W2["Seleccionar recepción, picking o control de stock"]
      W2 --> W3["Revisar objeto, lote y contexto actuales"]
      W3 --> W4{"¿El servidor confirma el hecho?"}
      W4 -->|Sí| W5["Mostrar confirmación y refrescar existencias"]
      W4 -->|No / incierta| W6["Recargar el objeto y verificar antes de reintentar"]
      W1 -. "cámara denegada" .-> W7["Usar búsqueda manual disponible"]
    end

    subgraph Logistics["Logistics — preparar y transferir una entrega"]
      L1["Revisar preparación, asignación y carga"] --> L2{"¿Hechos y versiones están vigentes?"}
      L2 -->|Sí| L3["Completar verificación y handoff de Dispatch"]
      L3 --> L4["Esperar aceptación independiente del Driver"]
      L4 --> L5{"¿Ambos hechos quedaron confirmados?"}
      L5 -->|Sí| L6["Mostrar responsabilidad vigente"]
      L2 -->|No| L7["Volver al proceso dueño para corregir o refrescar"]
      L5 -->|Respuesta incierta| L8["Consultar el estado; no repetir a ciegas"]
    end

    subgraph Driver["Driver — ejecutar una entrega asignada"]
      D1["Consultar Mis entregas y asignación"] --> D2{"¿La asignación sigue vigente?"}
      D2 -->|Sí| D3["Revisar instrucciones y registrar intento/evidencia"]
      D2 -->|No| D4["No iniciar; volver a Mis entregas y actualizar asignación"]
      D3 --> D5{"¿Permiso de ubicación concedido para la jornada?"}
      D5 -->|Sí| D6["Capturar ubicación dentro de la jornada permitida"]
      D5 -->|No| D7["No capturar ubicación; explicar limitación y ofrecer ajuste de permiso"]
      D3 --> D8{"¿Resultado remoto confirmado?"}
      D8 -->|Sí| D9["Mostrar resultado y POD como hechos separados"]
      D8 -->|No / incierto| D10["Consultar estado antes de volver a enviar"]
    end

    subgraph BOM["BOM — coordinar una excepción"]
      B1["Abrir Coordinar excepciones operativas"] --> B2["Revisar tipo, severidad, responsable y estado"]
      B2 --> B3{"¿La acción está dentro de la autoridad vigente?"}
      B3 -->|Sí| B4["Asignar o dar seguimiento; enrutar decisión al proceso dueño"]
      B3 -->|No / excepción vacía| B5["Mantenerla abierta o volver; no inventar un cierre"]
    end

    Hub --> O1
    Hub --> S1
    Hub --> W1
    Hub --> L1
    Hub --> D1
    Hub --> B1
```

##### Wireflows — entradas y pantallas Operations implementadas

El diagrama ubica las entradas y rutas actuales. Las opciones que una pantalla
abre como paso interno se señalan como rutas anidadas; no todas aparecen como
botones del hub. Una ruta que no supera la autorización vigente no se abre y el
estado protegido se invalida al cambiar el contexto o la autoridad.

##### Buyer — user flow y wireflow planificados en una aplicación separada

Buyer Mobile se proyecta como una aplicación Flutter/Dart independiente. Los
nodos de esta sección son diseño planificado; no corresponden a pantallas de
`CONNECTED_OPERATIONS`, no acreditan código implementado y no se consideran
recorridos ejecutados.

```mermaid
flowchart LR
    subgraph BuyerUser["User flow planificado — objetivo Buyer"]
      BU1["Consultar una entrega propia"] --> BU2["Verificar código de handoff"]
      BU2 --> BU3{"¿Código y entrega coinciden?"}
      BU3 -->|Sí| BU4["Comparar cantidades recibidas"]
      BU3 -->|No / no verificable| BU5["No confirmar; corregir o solicitar revisión"]
      BU4 --> BU6{"¿Las cantidades coinciden?"}
      BU6 -->|Sí| BU7["Confirmar Buyer Receipt"]
      BU6 -->|No| BU8["Registrar discrepancia separada"]
      BU7 --> BU9["Consultar resultado confirmado"]
      BU8 --> BU9
      BU9 -. "timeout o repetición" .-> BU10["Consultar el hecho original antes de reintentar"]
    end

    subgraph BuyerWire["Wireflow planificado — Buyer Mobile (Flutter/Dart)"]
      BW1["Pantalla prevista: actualización de entrega"] --> BW2["Pantalla prevista: verificación de código"]
      BW2 --> BW3["Pantalla prevista: cantidades realmente recibidas"]
      BW3 --> BW4{"¿Servidor confirma recepción?"}
      BW4 -->|Sí| BW5["Pantalla prevista: estado de receipt"]
      BW4 -->|Discrepancia| BW6["Pantalla prevista: reporte de discrepancia"]
      BW4 -->|Sin respuesta| BW7["Estado no confirmado; consultar antes de repetir"]
    end
```
