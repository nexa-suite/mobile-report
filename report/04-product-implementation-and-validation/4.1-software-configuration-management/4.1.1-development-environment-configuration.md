# Capítulo IV: Product Implementation & Validation

Este capítulo reúne la planificación de Sprint 1 y los criterios que permiten
distinguir una especificación académica de evidencia de implementación o
validación. No declara una aplicación Mobile ejecutada, una instalación en
dispositivo, una distribución ni sesiones de validación que no se acompañen de
su evidencia propia.

## 4.1. Software Configuration Management

### 4.1.1. Software Development Environment Configuration

| Recurso | Propósito en Nexa | Alcance documentado |
| :--- | :--- | :--- |
| Git y GitHub | Control de versiones, ramas, revisión y trazabilidad de cambios | El repositorio del informe se publica en `github.com/nexa-suite/mobile-report` |
| Planificación ágil | Organización de Sprint Goal, historias y tareas | Sprint Backlog 1 documenta planificación; no se declara ejecución de un tablero |
| Figma y UXPressia | Elaboración de artefactos de diseño e investigación | Esta entrega no adjunta wireframes, prototipos ni evidencia de investigación nueva |
| Lucidchart, Structurizr y PlantUML | Diagramas de arquitectura y flujos | Los diagramas del Capítulo II son referencias de diseño, no evidencia de runtime Mobile |
| Android Studio y Kotlin | Track Android/Kotlin planificado para Sprint 1 | No se declara un build Android producido |
| Flutter y Dart | Track Flutter/Dart planificado para Sprint 1 | No se declara un build Flutter producido; iOS queda fuera del alcance de Sprint 1 |
| Java, Spring Boot, PostgreSQL y OpenAPI | Contratos y servicios del backend de Nexa | Constituyen la referencia arquitectónica; no prueban consumo desde Mobile |
| HTML5, CSS3 y JavaScript | Superficie Website pública | El Website no sustituye evidencia de una aplicación Mobile |

Las tecnologías Mobile se presentan como tracks del plan de Sprint 1, no como
una selección silenciosa de un único cliente Mobile para todo el producto. Las
versiones concretas sólo deben informarse junto con un build o una configuración
reproducible que las sustente.
