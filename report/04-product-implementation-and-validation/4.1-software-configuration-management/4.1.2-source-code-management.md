### 4.1.2. Source Code Management

Los repositorios de Nexa utilizan Git y GitHub para gestionar
el código fuente, mantener el historial de modificaciones y
facilitar el trabajo colaborativo. El equipo emplea Pull Requests
para revisar e integrar los cambios, siguiendo una organización
de ramas basada en GitFlow.

Las ramas feature/* se utilizan para desarrollar nuevas
funcionalidades, mientras que las ramas release/* permiten
preparar versiones destinadas a main. En los repositorios
Mobile y API también se realizan sincronizaciones hacia
develop para mantener la continuidad del desarrollo.

*Repositorios que componen el alcance académico de Nexa.*

| Producto | Repositorio |
| --- | --- |
| Landing Page / Website | [nexa-suite/website](https://github.com/nexa-suite/website) |

| Web applications | [nexa-suite/web-clients](https://github.com/nexa-suite/web-clients) (monorepo Angular) |
| Mobile Applications | [nexa-suite/mobile](https://github.com/nexa-suite/mobile) |
| Academic Report | [nexa-suite/mobile-report](https://github.com/nexa-suite/mobile-report) |

**Evolución de las aplicaciones móviles**

El repositorio [Nexa Mobile](https://github.com/nexa-suite/mobile)
centraliza el desarrollo de Operations Mobile y Buyer Mobile.
Aunque ambas aplicaciones utilizan tecnologías diferentes,
comparten los mecanismos de control de versiones, revisión de
código y publicación de artefactos.

La publicación [Nexa Mobile v2.0.1](https://github.com/nexa-suite/mobile/releases/tag/v2.0.1)
incluye Operations Android `1.3.1` y Buyer Flutter `1.2.1+4`.
Estas versiones permiten identificar la implementación de
ambas aplicaciones dentro del mismo repositorio, manteniendo
sus respectivos procesos de construcción y distribución.

Las publicaciones de código permiten consultar las versiones
desarrolladas y los cambios integrados. Sin embargo, la
disponibilidad de una versión o de un archivo instalable no
garantiza que todos los procesos de negocio estén habilitados
ni que se hayan completado las pruebas de aceptación.

Semantic Versioning usa MAJOR para cambios incompatibles, MINOR para capacidad
compatible y PATCH para correcciones compatibles. Conventional Commits expresa
tipo y alcance, por ejemplo `docs(ch4): document source control`. Los cuatro
sprints académicos conservan su planificación y evidencia progresiva; la
asignación de un Sprint no declara por sí sola que el trabajo esté implementado
o aceptado.
