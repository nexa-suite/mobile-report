### 4.1.2. Source Code Management

Nexa emplea GitFlow para separar el trabajo de capítulo, la integración y la
preparación de una release. La rama no reemplaza la revisión académica ni la
verificación de los artefactos que contiene.

| Rama | Responsabilidad |
| :--- | :--- |
| `main` | Estado estable publicado; recibe una release aprobada |
| `develop` | Integración de cambios aprobados antes de preparar una release |
| `feature/*` | Cambio delimitado por capítulo o alcance de trabajo |
| `release/*` | Preparación y verificación de una versión candidata |
| `hotfix/*` | Corrección urgente derivada de una versión publicada |

El versionado sigue Semantic Versioning: `MAJOR` para cambios incompatibles,
`MINOR` para capacidad compatible y `PATCH` para correcciones compatibles. Los
commits usan Conventional Commits con tipo y alcance, por ejemplo
`docs(ch04): complete sprint one planning`.

El proceso de revisión conserva la rama de origen, el diff, las validaciones y
la firma del contribuidor responsable. Cada commit debe usar la identidad real
configurada para ese contribuidor; no se reemplaza la autoría mediante opciones
de Git. El repositorio público del informe es
<https://github.com/nexa-suite/mobile-report>.
