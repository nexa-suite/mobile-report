### 4.1.2. Source Code Management

Los repositorios usan Git y Pull Requests para revisar e integrar cambios. En
el GitFlow del equipo, las ramas `feature/*` integran incrementos en
`develop`; `release/*` prepara publicaciones para `main`. Mobile y API también
registran la sincronización de `main` hacia `develop` tras el release. La
secuencia más reciente y sus diferencias por repositorio se muestran abajo.

Las convenciones de nombres distinguen `feature/<area>` para incrementos
(por ejemplo, `feature/chapter-03` en el informe), `release/vMAJOR.MINOR.PATCH`
para preparar una versión y `hotfix/<correccion>` para una corrección urgente
de una versión publicada. Estos patrones describen el propósito de las ramas;
los releases observados se identifican en la tabla de publicaciones.

Semantic Versioning usa MAJOR para cambios incompatibles, MINOR para capacidad
compatible y PATCH para correcciones compatibles. Conventional Commits expresa
tipo y alcance, por ejemplo `docs(ch4): document source control`. Los cuatro
sprints académicos conservan su planificación y evidencia progresiva; la
asignación de un Sprint no declara por sí sola que el trabajo esté implementado
o aceptado.
