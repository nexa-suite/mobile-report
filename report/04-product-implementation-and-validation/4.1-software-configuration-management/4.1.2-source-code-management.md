### 4.1.2. Source Code Management

Nexa usa GitHub y GitFlow para organizar cambios revisables. Cada repositorio
mantiene su propio historial, mientras que el informe conserva enlaces a los
productos que forman la solución académica. El historial Git es evidencia de
cambio documental o técnico, pero no reemplaza la evidencia de ejecución,
validación con personas usuarias ni aceptación de producto.

#### Estado actual del flujo del informe

Después del hotfix publicado como `v0.1.1`, se restauró la topología GitFlow del
repositorio académico para aislar el trabajo por responsabilidad. Esta
restauración describe el estado actual de ramas; no se presenta como si hubiese
existido de forma continua en todo el historial anterior.

```text
main
└── develop
    ├── feature/front-master
    ├── feature/chapter-01
    ├── feature/chapter-02
    ├── feature/chapter-03
    ├── feature/chapter-04
    └── feature/report-integration
```

| Rama | Responsabilidad actual |
| --- | --- |
| `main` | Estado publicado estable. No recibe cambios directos de capítulos. |
| `develop` | Línea de integración previa a una preparación de release autorizada. |
| `feature/front-master` | Sólo `report/00-front-matter/**`. |
| `feature/chapter-01` | Sólo `report/01-presentation/**` y `report/assets/chapter-1/**`. |
| `feature/chapter-02` | Sólo `report/02-requirements-and-software-solution-design/**` y `report/assets/chapter-2/**`. |
| `feature/chapter-03` | Sólo `report/03-solution-ui-ux-design/**` y `report/assets/chapter-3/**`. |
| `feature/chapter-04` | Sólo `report/04-product-implementation-and-validation/**` y `report/assets/chapter-4/**`. |
| `feature/report-integration` | Navegación, composición y validadores globales; no reescribe semántica de capítulos. |

Las ramas `release/*` y `hotfix/*` se reservan para una preparación o corrección
autorizada de una versión publicada. No se fuerza una publicación, merge, Pull
Request o tag sólo para completar el informe académico.

#### Controles de cambio

| Control | Aplicación |
| --- | --- |
| Actualización de referencia | Antes de integrar o publicar, se consulta el remoto y se detiene el flujo si una rama divergió. |
| Alcance | Cada cambio se realiza en la rama propietaria; los cambios globales usan la rama de integración. |
| Autoría | Los commits materiales usan la identidad real y la firma configurada para la persona contribuyente. La firma se verifica con las herramientas autorizadas, no por afirmación textual. |
| Revisión | Un diff, su validación y su rama fuente se conservan antes de cualquier Pull Request autorizada. |
| Seguridad de historial | No se usa force-push, rebase compartido, merge automático ni modificación de tags sin autoridad SCM explícita. |

Semantic Versioning usa MAJOR para cambio incompatible, MINOR para capacidad compatible y PATCH para corrección compatible. Conventional Commits expresa tipo y alcance, por ejemplo `docs(ch04): clarify scm branch restoration`. Los cuatro sprints académicos se mantienen como planificación y evidencia progresiva: una asignación de Sprint no declara que el trabajo esté implementado o aceptado.
