### 4.1.2. Source Code Management

Nexa usa GitHub y GitFlow para organizar cambios revisables. Cada repositorio
mantiene su propio historial, pero el informe conserva enlaces a los productos
que forman la solución académica.

| Producto | Repositorio |
| --- | --- |
| Landing Page / Website | [nexa-suite/website](https://github.com/nexa-suite/website) |
| Web Services | [nexa-suite/api](https://github.com/nexa-suite/api) |
| Mobile Applications | [nexa-suite/mobile](https://github.com/nexa-suite/mobile) |
| Academic Report | [nexa-suite/mobile-report](https://github.com/nexa-suite/mobile-report) |
| Internal operational Web application | [nexa-suite/platform](https://github.com/nexa-suite/platform) |
| Buyer-facing Web application | [nexa-suite/portal](https://github.com/nexa-suite/portal) |

| Branch | Responsibility |
| --- | --- |
| main | Stable published state after approved review and validation. |
| develop | Integrates approved changes before release preparation. |
| feature/* | Delimits one feature, chapter, or cohesive scope. |
| release/* | Prepares and verifies a candidate version. |
| hotfix/* | Corrects a published version without mutating its tag. |

Semantic Versioning uses MAJOR for incompatible change, MINOR for compatible
capability, and PATCH for compatible correction. Conventional Commits use a
type and scope, for example `docs(ch04): replan sprint one scope`. Pull Requests
retain source branch, diff, review and validation evidence; commits keep the
real contributor identity configured for that change.
