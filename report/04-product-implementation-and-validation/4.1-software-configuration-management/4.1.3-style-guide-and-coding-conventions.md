### 4.1.3. Source Code Style Guide & Conventions

Los repositorios Nexa usan inglés para identificadores, contratos y nombres de
archivo. El Website mantiene contenido público en español e inglés mediante
sus claves de traducción; el texto localizado no cambia los nombres internos
del código.

*Convenciones y controles observados en los repositorios vigentes.*

| Lenguaje o formato | Convenciones del código | Rutas y controles existentes |
| --- | --- | --- |
| HTML5 — Website | Organizar cada página como documento semántico; mantener páginas independientes bajo `pages/` y marcar el idioma y las etiquetas accesibles del contenido. El Website conecta texto y etiquetas mediante atributos como `data-i18n` y `data-i18n-aria-label`. | [`index.html`](https://github.com/nexa-suite/website/blob/v1.0.0/index.html), [`pages/`](https://github.com/nexa-suite/website/tree/v1.0.0/pages) y [`assets/js/i18n.js`](https://github.com/nexa-suite/website/blob/v1.0.0/assets/js/i18n.js). La publicación v1.0.0 registró comprobación de páginas y referencias locales. |
| CSS3 — Website | Centralizar colores, espaciado, radios y contenedores como custom properties; reutilizar los valores en hojas separadas por tipografía, layout, componentes y precios. Ejemplos existentes: `--c-primary`, `--space-4` y `--radius-md`; para valores adaptables se emplea `clamp()`. | [`assets/css/tokens.css`](https://github.com/nexa-suite/website/blob/v1.0.0/assets/css/tokens.css), `layout.css`, `components.css` y `typography.css`. La release v1.0.0 registra vistas de escritorio y móvil; el sitio se publica como contenido estático. |
| JavaScript — Website | Mantener JavaScript nativo, sin framework ni bundle; usar `camelCase` para funciones y variables, y constantes compartidas en `UPPER_SNAKE_CASE`. El selector de idioma se concentra en `getStoredLang` y `applyLanguage` con `STORAGE_KEY`. | [`assets/js/i18n.js`](https://github.com/nexa-suite/website/blob/v1.0.0/assets/js/i18n.js), `interactions.js` y `animations.js`. La verificación de v1.0.0 incluyó sintaxis de tres scripts; GitHub Actions ejecuta lint de Markdown y de commits. |
| Java — API | Mantener tipos en `PascalCase`, métodos y variables en `camelCase`, y paquetes en minúsculas. La implementación es un monolito modular Spring Boot; los módulos de código organizan el servicio. | [`pom.xml`](https://github.com/nexa-suite/api/blob/v1.0.0/pom.xml) define Java 25, Spring Boot 4.1.1 y Maven; Surefire ejecuta pruebas. La release v1.0.0 documenta `mvn clean verify` y pruebas unitarias y de integración. |
| Kotlin — Operations Android | Usar `PascalCase` en tipos, `lowerCamelCase` en funciones y propiedades, y `PascalCase` en funciones `@Composable`. El `.editorconfig` raíz aplica sangría de cuatro espacios y estilo `android_studio`; separar app, `core` y módulos `feature` con dependencias dirigidas a gateways/repositorios. | [`.editorconfig`](https://github.com/nexa-suite/mobile/blob/v1.0.1/.editorconfig), `apps/operations-android`, `core/auth`, `core/network`, `feature/warehouse` y `feature/dispatch`. El README de [Operations Android](https://github.com/nexa-suite/mobile/blob/v1.0.1/apps/operations-android/README.md) registra `ktlintCheck`, `lintDebug`, `verifyAndroidArchitecture`, verificación estricta de dependencias, pruebas JVM e instrumentación Android. |
| Dart / Flutter — Buyer Mobile | Para el target Buyer Mobile, usar `PascalCase` en tipos y `lowerCamelCase` en miembros; aplicar `dart format` al establecer el módulo Flutter. | Buyer Mobile permanece como objetivo `TARGET`. |
| Markdown — informe | Usar títulos jerárquicos, enlaces relativos para archivos del informe y texto alternativo descriptivo para imágenes. Cada tabla debe reunir datos comparables y conservar su fuente. | `.markdownlint-cli2.jsonc` configura el lint del repositorio; `.github/CONTRIBUTING.md` describe los controles previos a revisión. |

El Website es código estático y organiza contenido, estilos y scripts en
archivos separados. El API compila y valida sus módulos mediante Maven. En
Operations Android, `ktlint` y Android Lint complementan el verificador de
límites entre módulos y las pruebas automatizadas. Los controles se describen
por repositorio; el estado concreto de cada release se conserva en sus
respectivos registros.
