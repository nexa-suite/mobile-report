#### 4.2.1.7. Services Documentation Evidence for Sprint Review

Durante el Sprint 1 se identificaron los servicios REST
necesarios para las funcionalidades iniciales de
Operations Mobile, principalmente la autenticación,
la gestión de sesiones, la confirmación del contexto
autorizado y la resolución de identificadores de productos.

La documentación de estas interfaces se encuentra
versionada en el [repositorio Nexa API](https://github.com/nexa-suite/api/tree/develop/docs/openapi).
Su utilización permite establecer la relación entre
las funcionalidades de la aplicación móvil y las
operaciones proporcionadas por el servidor.

Operations Mobile actúa como cliente de estos servicios,
mientras que Nexa API conserva la responsabilidad de
verificar la identidad, la sesión, la pertenencia al
Tenant y Workspace, los permisos y la resolución de
identificadores de productos.

La siguiente tabla presenta las operaciones relacionadas
con Sprint 1, sus parámetros principales y las
respuestas definidas en los contratos.

*Contratos de servicio relacionados con Sprint 1*

| Método y ruta | Parámetros / body observado | Respuesta y significado | Relación con Sprint 1 |
| --- | --- | --- | --- |
| `POST /api/v1/authentication/sign-in` | `identifier`, `password`, `workspaceSlug`, `surface`; cliente nativo con `ClientSurface.PLATFORM` y `X-Nexa-Client: NATIVE`. | HTTP 200 con access token, expiración y sesión. | `MOB-US-001`; `TS-MOB-001` |
| `POST /api/v1/authentication/refresh` | Refresh token y marker de superficie. | HTTP 200 con header refresh de reemplazo; un refresh fallido invalida la sesión. | `MOB-US-001`; `TS-MOB-001` |
| `POST /api/v1/authentication/sign-out` | Bearer y superficie; sin body. | HTTP 204 para cierre de sesión. | `MOB-US-001`; `TS-MOB-001` |
| `GET /api/v1/session` | Bearer de sesión vigente. | HTTP 200 con usuario, Tenant, Workspace, membership y surface confirmados por servidor. | `MOB-US-002`, `MOB-US-003`; `TS-MOB-001` |
| `GET /api/v1/skus/resolve?identifier=<value>` | Query `identifier`, bearer y visibilidad Tenant/Workspace. | Conserva `RESOLVED`, `NOT_FOUND` o `AMBIGUOUS`; una respuesta ambigua no selecciona `skuId`. | `MOB-US-011`; `TS-MOB-007` |

En el proceso de identificación de productos, la cámara
del dispositivo permite capturar y decodificar el
contenido del código. La resolución del identificador
corresponde al API, que determina el resultado según
el contexto y los permisos del usuario. Cuando existen
coincidencias ambiguas, la aplicación no debe asumir
una identificación definitiva del producto.

Las operaciones descritas constituyen la referencia
técnica para las funcionalidades iniciales de
Operations Mobile. Los resultados de las comprobaciones
realizadas en el entorno aislado se presentan en la
sección 4.2.1.6. Por su parte, las capturas de
Swagger UI del servicio publicado se documentan
en la sección 4.2.2.7, correspondiente a Sprint 2.
